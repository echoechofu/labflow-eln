# Protocol 模块化交付与验收

目标：自定义配置能够表达当前 11 个内置 Protocol 的行为，复用现有领域模型、共享 service、Record snapshot 和事务。能力相同不代表生成的 UUID 或日期相同；验收比较输入输出关系、类型、数量、usage、正文和检测配置。

## 分工

| 工作 | 负责人 | 验收依据 |
| --- | --- | --- |
| 现有能力清单与案例整理 | 轻量模型，统筹复核 | catalog、执行器与测试三方一致 |
| 行为保持型 React 组件提取 | 轻量模型，统筹审查 diff | props/state/提交参数保持，构建与测试通过 |
| 字段、布局、预览组件实现 | 轻量模型，接口确定后分配 | 字段显隐、必填、输入模式切换与实际执行一致 |
| schema 兼容与完整版本更新契约 | 统筹 | 旧 schema 可读，历史 snapshot 不变，非法组合拒绝 |
| 输入解析、输出与 consumption 能力统一 | 统筹 | 精确 lineage、类型、数量及失败事务回滚 |
| Terminal Assay 与分析能力绑定 | 统筹 | 不把任意指标误当 qPCR，不制造不存在的分析能力 |
| MCP adapter 对齐 | 接口确定后可交轻量模型，统筹复核 | 同一 service，结构化契约测试 |
| 最终集成与交付验收 | 统筹 | 不依赖执行者自报；独立代码审查与检查 |

## 阶段与边界

1. 当前批次：提取 Record 创建抽屉，形成能力对照表。此批次不宣称完成自定义能力覆盖。
2. 将字段渲染、Sample 选择、外部登记、条件分配和孔板布局继续拆成组件，保留一个 Record 创建状态与提交入口。
3. 设计受限、可验证的配置契约；实现完整配置创建和版本更新，保留旧请求兼容；先写能力等价和非法组合的服务测试。
4. 从现有执行器提炼可组合能力。保持一次事务执行，不拆成多个独立提交的工具调用。内置特殊输出与 metadata 规则必须逐项迁移。
5. 编辑器开放字段、输入输出、模板变体、检测配置及复制内置功能；Desktop 与 MCP 使用相同契约。
6. 逐个内置运行等价自定义配置，对比结果，验证历史版本、重启、删除保护与导出；完成桌面交互验收后再打包。

## 初始审计约束（第二批进展见下文）

- 不能直接给所有内置配置加上 `sample_flow_v1`：现有 metadata 合并行为存在差异。
- `plate_or_dish` 按参数选择输出类型；`plate_wells` 对 PLATE 生成 WELL，对其他支持类型继续输出原 Sample。
- lineage 的刺激历史查询识别 `event_type='treatment'`，能力统一须保留该语义或提供兼容查询；不能只比较输出数量。
- 自定义 `same_sample` 和刺激透传保留最初创建来源。直接父 Task 分组依据其 Record.outputs。
- qPCR 目前通过指标 `cq` 进入专属分析；扩大自定义检测前应明确分析能力绑定及适用条件。
- 初始版本的自定义版本编辑只替换正文；第二批已扩展来源能力、字段与模板变体的版本更新，仍不开放任意执行规则组合。
- 初始执行器的通用必填验证只检查非空。第二批已统一显隐条件、数字有限性、选项合法性、字段 key 唯一性和模板引用验证；不能把前端显隐当作后端验证。
- 任意 JSON 编辑器和用户脚本不属于交付方案；用户选择已实现且经过验证的能力。
